# docs/review — 리뷰 결과 보관

**성격:** 설계·코드에 대한 **리뷰 산출물** (규율도, 조사 원자료도, 진행 보고도 아닌
「제3자 시선의 지적」).

- **리뷰어(도구·사람)별 하위 폴더로 나눈다** — [`gstack/`](gstack/) ·
  [`oh-my-claudecode/`](oh-my-claudecode/). 리뷰어를 더 붙이면 형제 폴더를 만든다.
  🧭 **왜 나누나**: 리뷰어마다 보는 것과 놓치는 것이 다르다. 섞어 두면 「이 지적이 어디서
  나왔나」를 잃고, 그러면 「이 도구는 이 자리를 못 본다」는 것도 못 배운다.
- 파일명: `REVIEW_<YYYY-MM-DD>_<주제>.md`.
- 리뷰 지적이 **수용·확정**되면 그 결론은 [`../DATA_CONTRACT.md`](../DATA_CONTRACT.md) ·
  [`../API_CONTRACT.md`](../API_CONTRACT.md) · [`../rules/`](../rules/) ·
  [`../../TODOS.md`](../../TODOS.md) 로 **승격**하고, 리뷰 원문은 여기 남긴다.
- 🔴 **승격한 뒤에는 리뷰 문서를 근거로 인용하지 않는다.** 정본을 인용한다.
- 여기 두지 말 것: 일일 진행 리포트(→ [`../reports/daily/`](../reports/daily/)),
  조사 원자료(→ [`../research/`](../research/)).

## 🔴 리뷰는 원본을 남긴다 — 최소 구성

리뷰를 한 세션은 **그 세션 안에서** 문서를 남긴다. 나중에 쓰면 안 쓴다.

| 반드시 | 내용 |
| --- | --- |
| 대상 | 어느 브랜치·어느 파일·어느 시점 |
| 범위 | 무엇을 봤고 **무엇을 안 봤나** |
| 방법 | 코드를 읽었나, 돌려 봤나, 문서만 봤나 |
| 심각도 범례 | 🔴/🟠/🟡 가 각각 무슨 뜻인지 |
| **지적 전체 표** | 건별로 지적 + 결정 |
| 버린 것 | 반려·보류한 지적과 **그 이유** |
| 남은 위험 | 이번에 안 본 것 |

## 🔴 「문제다」라고 쓰기 전에 근거 등급을 붙인다

리뷰 지적은 **돌려 본 것**과 **코드를 읽은 것**과 **라이브러리 동작으로 유추한 것**이
신뢰도가 전혀 다르다. 안 구분하면 다음 사람이 셋을 다 「확인된 결함」으로 읽고,
그중 하나가 틀렸을 때 리뷰 전체를 못 믿게 된다.

| 근거 등급 | 어떻게 적나 |
| --- | --- |
| **확인함** | 돌려 봤거나 검사로 재현했다 — 어떻게 했는지 함께 |
| **코드 대조** | 해당 줄을 읽고 판단했다 — `파일:줄` 과 함께 |
| ⚠️ **추정** | 라이브러리·프레임워크 동작을 근거로 유추했다 — **실물 확인 필요**로 표시 |

```
📌 2026-08-27, 실제로 그랬다 — 그리고 끝까지 가 봤다

   ① 답안 제출 응답의 「isCorrect」 키가 Jackson 규칙 때문에 실제로는 「correct」로
      나갈 것 같았다. JDK 가 없어 못 돌려봤으므로 ⚠️추정 으로 남겼다.
   ② 외부 근거로 규칙을 확정했다. 등급이 「확인함」으로 올라갔고,
      「지금 화면이 정답을 오답으로 보여준다」는 🔴 P1 지적이 됐다.
   ③ 🔴 그런데 프론트엔드를 열어 보니 **이미 「correct」로 받고 있었다.**
      멀쩡히 돌아가고 있었고, 자바를 고치면 오히려 깨지는 상태였다.
```

🎯 **여기서 배울 것은 두 가지다.**
- **①→② 는 옳았다.** 모르는 것을 ⚠️ 로 남겨 두었기에 나중에 확정할 수 있었다.
- 🔴 **②→③ 이 실패였다.** 「규칙이 이렇다」(사실)에서 「그래서 화면이 깨져 있다」(결론)로
  건너뛰었다. **계약은 양쪽이 있고, 한쪽만 보고는 결론이 안 나온다.**
  프론트가 별도 폴더라 「범위 밖」이었는데, **범위 밖인 것과 결론을 낼 수 있는 것을
  혼동했다.**

📌 **범위 밖이면 결론도 유보한다.** 「A 는 이렇다」까지만 적고, 「그래서 B 가 깨진다」는
B 를 본 뒤에 적는다. 전말: [gstack 리뷰의 결정 기록](gstack/REVIEW_2026-08-27_plan-eng-review.md)

## 🔴 지적 표를 「남은 일 목록」으로 읽지 말 것

리뷰 문서의 지적 표는 **리뷰 당일의 사진**이다. 처리해도 그 표는 안 바뀐다 —
**원본은 그날의 기록이라 고치지 않는 것이 규율**이기 때문이다.

```
⚠️ 형제 앱(job-signal)에서 실제로 그랬다
   리뷰 20건의 「결정」 칸이 전부 「대기」로 남아 있었는데,
   코드로 확인해 보니 8건이 이미 끝났고 1건은 지적 자체가 틀렸다.
   그대로 뒀으면 다음 리뷰가 **이미 고친 것을 다시 지적**한다.
```

그래서 리뷰를 **처리한** 세션은 두 가지를 반드시 한다.

1. **문서 끝에 「결정 기록」을 이어 붙인다** — 건별로 `처리 · 확인한 자리(파일:줄) · 근거`.
   🧭 「고쳤다」만 적지 않는다. **어디를 보면 확인되는지**가 있어야 다음 사람이 다시 안 판다.
2. **지적 표 위에 안내를 단다** — *"결정 칸은 그날 상태다. 확정 결과는 문서 끝을 본다."*

📌 **「지적이 틀렸다」도 결정이다.** 버린 이유를 적어 두지 않으면 다음 리뷰가 같은 것을
다시 가져온다.
📌 **아직 안 본 것**은 결정 기록에 `🔴 그대로`로 남기고
[`../../TODOS.md`](../../TODOS.md) 에 올린다 — 조용히 빠지면 「다 끝났다」로 읽힌다.

## ⚠️ 이 프로젝트에서 특히 주의할 것

리뷰어가 자주 **범위 밖을 지적한다.** 아래는 지적이 아니라 **이미 정해진 것**이니,
받으면 결정 기록에 「반려 — 근거 링크」로 적고 넘어간다.

| 자주 나오는 지적 | 실제로는 |
| --- | --- |
| 「단답형 자가채점은 취약하다」 | 알고 있다. 세 안의 대가까지 정리돼 있고 **사용자가 정할 일**이다 → [`../rules/grading-and-difficulty.md`](../rules/grading-and-difficulty.md) §4 |
| 「`chapter_title` 은 자바 관례에 안 맞다」 | FastAPI 계약이 snake_case 라 **의도된 것**이다 → [`../API_CONTRACT.md`](../API_CONTRACT.md) §7 |
| 「`supabase` 의존성이 안 쓰인다」 | 맞다. Phase 3 자리이고 이미 기록돼 있다 → [`../PRD.md`](../PRD.md) §2-⑥ |
| 「`ddl-auto: update` 를 바꿔라」 | 맞다. 다만 **마이그레이션 도구 선택은 사용자 결정**이다 → [`../../TODOS.md`](../../TODOS.md) 8절 |
