# docs/review/gstack — gstack 리뷰 결과

**성격:** gstack 스킬(`/review` · `/plan-eng-review` · `/plan-ceo-review` · `/design-review`
· `/cso` 등) 경로로 수행한 설계·코드 리뷰 산출물.

- 파일명: `REVIEW_<YYYY-MM-DD>_<스킬 또는 주제>.md`.
- 리뷰 문서 상단에 **대상(문서·커밋 범위)·리뷰 시점 국면·방식·심각도 범례**를 기록해,
  나중에 읽어도 「무엇을 기준으로 지적했는지」를 알 수 있게 한다.
- **gstack 리뷰의 특성**: 대화형이다 — 지적마다 선택지를 제시하고 사용자가 즉석에서
  확정하므로, 리뷰 문서에 **각 지적의 확정 결과(고른 선택지·반영 위치)까지 함께 기록**된다.
  즉 이 폴더의 문서는 「지적 원문 + 결정 로그」를 겸한다.
  (수용된 결론의 **정본**은 여기가 아니라 승격 위치다 — 아래.)
- 수용·확정된 항목의 결론은 [`../../DATA_CONTRACT.md`](../../DATA_CONTRACT.md) ·
  [`../../API_CONTRACT.md`](../../API_CONTRACT.md) · [`../../rules/`](../../rules/) ·
  [`../../../TODOS.md`](../../../TODOS.md) 로 **승격**하고, 리뷰 원문은 여기 남긴다
  (상위 [`../README.md`](../README.md) 규율).

## 🔴 gstack 이 만든 별도 산출물은 **부록으로 원문 이관**

`/plan-eng-review` 같은 스킬은 리뷰 대화와 별개로 **테스트 플랜 파일**을
`~/.gstack/projects/...` 에 만든다.

🔴 **리뷰 문서에 그 경로만 적어 두면 기록이 아니다.** 레포 밖 로컬 캐시라 다른 사람
머신엔 없고, gstack 재설치·정리 한 번에 사라진다.

```
⚠️ 형제 앱(job-signal)에서 실제로 그랬다
   경로만 적힌 산출물 두 건이 그대로 방치돼 있었다.
```

- **규칙**: 리뷰 문서 말미에 `## 부록 A — 테스트 플랜 원문` 을 두고 **코드펜스로 원문
  그대로** 옮긴다. 🔴 **요약하지 않는다** — 요약하면 「무엇을 검증하기로 했는지」의
  원본이 사라진다.
- **원문은 고치지 않는다.** 이후 확정으로 달라진 부분은 **각주**로 아래에 적고 정본 링크를
  건다. 리뷰 원문을 사후 편집하면 「그때 무엇을 알고 있었나」가 없어진다.
- **귀속을 확인한다.** 같은 날 세션이 여러 번 돌 수 있다. 파일명 타임스탬프는 **로컬 시각**,
  기록 파일은 **UTC** 인 경우가 있어 그대로 비교하면 어긋난다. 전용 리뷰 문서가 없는
  세션의 산출물은 **가장 가까운 리뷰 문서에 부록으로** 두고 귀속을 명시한다.

## ⚠️ 이 프로젝트에 gstack 을 돌릴 때

- **`/browse` · `/qa` 계열은 이 레포에서 못 쓴다.** 프론트엔드가 이 레포에 없다
  ([`../../PRD.md`](../../PRD.md) §3). 화면 QA 를 하려면 별도 레포가 필요하다.
- **`/review` 는 브랜치 diff 를 본다.** 지금 작업 트리에는 이전 세션의 미커밋 변경이
  섞여 있을 수 있으니, 리뷰 문서 상단에 **대상 커밋 범위를 반드시 적는다.**
- 🔴 **이미 정해진 것을 다시 지적받으면 반려하고 근거를 링크한다.**
  자주 나오는 네 가지 목록: [`../README.md`](../README.md) 「이 프로젝트에서 특히 주의할 것」
