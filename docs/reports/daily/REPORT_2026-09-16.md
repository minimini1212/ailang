## §4 🔴 같은 파일 두 줄 차이로 정책이 반대였다

§3 에서 「학년 어휘가 다섯 곳에 있다」를 재면서, 그중 두 곳을 열어 보다가 찾았다.

```python
grade_name = GRADE_DISPLAY.get(grade, grade)          # ← 모르면 «그대로 넘긴다»
# 🔴 어휘 밖의 값을 기본값으로 접지 않는다. 조용히 「중간」으로 바꿔치기하면 ...
if difficulty not in DIFFICULTY_DISPLAY:               # ← 모르면 «거부한다»
    raise LlmBadResponseException(...)
```

🎯 **주석이 바로 위 줄이 하는 일을 금지하고 있었다.** 난이도는 모르는 값을 거부하는데,
두 줄 위의 학년은 조용히 접고 있었다.

**무엇이 문제였나 (역할 → 작용 → 결과)**

```
학년 이름을 못 찾으면 → 학년 «코드» 를 그대로 돌려준다
  → 프롬프트에 「학생 학년: MIDDLE_4」 가 실린다
  → 모델은 그 말을 «알아들은 척» 답한다
  → 🔴 에러가 어디서도 안 난다. 학생은 자기 수준과 안 맞는 설명을 받는다
```

### 무엇을 했나

**결정이 필요한 부분은 건드리지 않았다.** 「FastAPI 가 학년명을 Spring 에게서 받을지」는
서버를 나눈 대가 자체라 열어 뒀다. 대신 **이미 정해져 있는 규칙**(「모르는 값을 접지
않는다」)을 **일관되게** 적용했다 — 바로 아래 난이도 줄이 그 규칙의 본보기였다.

| | 전 | 후 |
| --- | --- | --- |
| 학년 어휘가 몇 곳에 | **다섯** | **셋** (파이썬 두 벌을 한 곳으로) |
| 모르는 학년이 오면 | 🔴 조용히 코드를 프롬프트에 넣는다 | **거부한다** |
| 모르는 난이도가 오면 | 거부한다 | 거부한다 (그대로) |

새 파일 `ai-server/app/vocabulary.py` 하나가 생겼고, 두 서비스가 그것을 쓴다.
⚠️ 그 파일 맨 위에 **「여기 있는 값은 정본이 아니다」**라고 적어 뒀다 — 정본은 여전히
Spring 의 enum 이다.

## §5 🔴 살려 온 실패의 종류를 «마지막 한 칸» 에서 뭉개고 있었다

§4 를 하고 나서 화면 쪽에 남아 있던 에러 처리 네 곳을 마저 옮기다가 찾았다.

개념 설명 화면은 실패를 이렇게 다루고 있었다.

```
400 이면   → 화면이 «자기 문구» 를 쓴다
429 이면   → 화면이 «자기 문구» 를 쓴다
그 밖에는  → 전부 「개념 설명을 받지 못했습니다」
```

**그래서 이렇게 됐다.**

| 서버가 보낸 것 | 뜻 | 학생이 본 것 |
| --- | --- | --- |
| `502` 「AI 응답을 처리하지 못했습니다. 다시 시도해 주세요」 | **다시 눌러 보면 될 일** | 개념 설명을 받지 못했습니다 |
| `503` 「AI 기능을 일시적으로 이용할 수 없습니다」 | **기다려야 하는 일** | 개념 설명을 받지 못했습니다 |

🔴 **이 둘을 나누려고 백엔드가 하는 일이 꽤 많다.** 챗봇 서버가 실패를 네 종류로 나누고,
메인 서버가 그것을 429·502·503 으로 **보존한다** — 그러려고 「모든 예외를 500 으로
바꾸는 그물」보다 **앞에서** 분류한다. 그 노력이 **마지막 한 칸에서 사라지고 있었다.**

⚠️ `400` 도 문제였다. 화면이 지어낸 문구가 서버 것보다 **덜** 완전했다.

```
서버  「학년을 먼저 설정해 주세요. 마이페이지에서 «학년을» 고를 수 있어요」
화면  「학년을 먼저 설정해 주세요. 마이페이지에서 고를 수 있어요」
```

🎯 **같은 말을 두 곳에 적어 두면 한쪽만 다듬게 되고, 학생이 보는 것은 안 다듬은 쪽이다.**

### 무엇을 바꿨나

문구를 **지어내지 않고 서버가 보내 주는 것을 그대로** 보여 준다.

🎯 **한 곳만 예외로 남겼다** — 「이 단원에는 아직 풀 수 있는 문제가 없습니다」.
서버는 「해당 조건에 맞는 문제가 없습니다」라고만 하는데, **화면은 어느 단원인지를
알고 있다.** 화면이 «더 잘» 말할 수 있는 자리는 화면이 말한다.

그리고 어제 만든 「실패를 읽는 자리」를 **다섯 곳이 모두** 쓰게 됐다. 인라인으로 흩어져
있던 에러 모양 선언은 이제 없다.

⚠️ 세션 확인과 인터셉터에서도 같은 것을 고쳤다 — **응답이 «아예 없는» 것(네트워크 끊김)과
서버가 401 을 «준» 것은 다른 일이다.** 앞에서 재발급을 시도하면 헛수고다.

### 검사 3건

```
🔴 502 와 503 이 «다른 말» 로 보이는가
🔴 둘 다 준비된 문구로 «떨어지지» 않는가
🎯 서버가 «더 완전한» 문구를 주면 그것을 쓰는가
```

두 번째가 핵심이다 — 서버 문구를 무시하고 화면 문구를 쓰면 **둘 다 같은 fallback 이 되어
첫 번째 검사도 함께 깨진다.**

## §6 🔴 화면이 실패를 「없음」으로 접고 있었다

§5 를 하면서 **손대지 않은 화면들도 훑었다.** 남은 자리들은 에러를 **아예 받지 않는**
`catch {}` 였고, 그중 둘이 이 저장소의 HARD 규칙에 정면으로 걸렸다.

### ① 홈 화면 — 실패가 «빈 목록» 이 됐다

```js
.catch(() => setChapters([]))
```

단원 목록을 못 불러오면 빈 배열이 됐고, 화면은 이렇게 말했다.

> 챕터 정보가 없습니다.

🔴 **그 학년에 «정말로» 단원이 없는 것과, 요청이 «실패한» 것이 학생에게 똑같이 보였다.**
기다리면 되는지, 다시 눌러야 하는지, 원래 없는 건지 알 방법이 없다.

⚠️ **어제 백엔드를 고치면서 이 경로가 새 상태를 내기 시작했다** — 학년 없이 비로그인이면
`401`, 어휘 밖 학년이면 `400`. 둘 다 여기서 「챕터 정보가 없습니다」로 조용히 사라졌을
것이다. 🎯 **한쪽을 고치면 다른 쪽이 그것을 삼키고 있지 않은지 봐야 한다.**

고친 방식: 두 상태를 **따로 들고**, 「못 불러왔다」를 「없다」보다 **먼저** 말한다.
⚠️ 비로그인은 «실패가 아니다» — 그 자리는 오류 문구를 띄우지 않는다.

### ② 진단 테스트 — 「완료 저장 실패」를 아무 말 없이 삼켰다

```js
await completeAssessment();
updateUser({ assessmentCompleted: true });
} catch {
  // 완료 처리 실패해도 결과 화면은 표시
}
```

🎯 **결과 화면을 보여 주는 판단 자체는 옳다** — 20문제를 푼 학생에게서 결과를 뺏으면
안 된다. 문제는 **아무 말도 안 한다**는 것이다.

```
저장이 실패한다 → 서버에는 「진단 완료」가 안 남는다
                → 다음에 로그인하면 20문제를 «처음부터 다시» 받는다
                → 🔴 학생은 왜 또 푸는지 모른다
```

고친 방식: 결과는 그대로 보여 주고, 그 위에 **저장이 안 됐다**를 적는다.

### 🔴 ③ 그리고 내가 세지 않고 적었다

②를 커밋하면서 「이제 에러를 안 받는 `catch {}` 는 한 곳만 남는다」고 적었는데,
**세어 보니 여섯 곳**이었다. 맞춤 문제 화면을 「이미 고쳤다」고 생각하고 다시 안 봤는데,
§5 에서 고친 것은 그 파일의 **두 자리뿐**이었다.

🎯 **「그 파일은 봤다」와 「그 파일을 다 봤다」는 다른 말이다.**

다시 세어 넷으로 줄였고, **남은 넷은 삼키는 것이 맞는 자리**다 — 넷 다 «다음 수단이
있는» 실패이고, 그 사실이 주석에 적혀 있거나 코드로 보인다.

| 남은 자리 | 왜 삼켜도 되나 |
| --- | --- |
| 재발급 실패 | 로그아웃 처리로 **넘어간다**. 문구를 보여 줄 화면이 없다 |
| 수식 렌더 실패 | 원본 글자를 보여 준다. 🎯 못 그리는 것과 **아무것도 안 보이는** 것은 다르다 |
| 보기 JSON 파싱 (2곳) | 다음 방법으로 넘어간다. 「지어내지 않는다」 |

## §7 🔄 「주석으로만 막아 뒀다」를 닫았다 — 그리고 또 하나 나왔다

§6 을 커밋하면서 이렇게 적었다.

> 🔴 두 결함이 다시 생겨도 **검사가 잡아 주지 않는다** — 주석으로만 막아 뒀다.

그 자리를 닫았다. 바꾼 것이 컴포넌트 상태와 렌더 분기라 순수 함수 검사로는 닿지 않아,
**컴포넌트 검사 도구**(화면을 실제로 그려 보고 「무엇이 보이나」를 확인하는 도구)를 들였다.

⚠️ **그래도 순수 로직은 여전히 순수 함수로 뺀다.** 컴포넌트 검사는 느리고(1건에 1초쯤)
깨지기 쉬우므로 **「화면이 무엇을 보여 주는가」가 판단의 핵심일 때만** 쓴다.

### 검사 12건 (43 → 55)

| 어디 | 몇 건 | 무엇을 못 박나 |
| --- | ---: | --- |
| 홈 | 6 | 「못 불러왔다」와 「없다」를 **다르게** 말하는가. 비로그인은 **실패가 아니다** |
| 진단 | 5 | 저장이 실패해도 결과는 보여 주되 **말은 하는가**. 그때 로그인 상태도 완료로 **안 바꾸는가** |
| 수식 파서 | 1 | 아래 참고 |

### 🔴 검사를 쓰다가 결함 하나가 더 나왔다

진단 결과 화면이 **통째로** 터졌다. 따라가 보니 수식 파서가 **값 없음에서 죽고** 있었다.

```
parseSegments(undefined) → text.length 를 읽는다 → 터진다 → 화면 «전체» 가 사라진다
```

이번에는 내 검사 픽스처가 필드 이름을 틀려서 났지만(`correctAnswer` 를 `answer` 로),
🔴 **서버가 그 필드를 `null` 로 보내거나 빼면 실제로 같은 일이 난다.** 타입은 문자열로
적혀 있지만 런타임에는 그대로 들어온다.

🎯 **못 그리는 것과 «아무것도 안 보이는» 것은 다르다** — 이 파일은 이미 수식 렌더
실패를 그렇게 다루고 있었다(원본 글자를 보여 준다). 같은 판단을 맨 앞에도 뒀다.

⚠️ **픽스처도 고쳤다.** 검사 픽스처가 서버 응답과 **모양이 다르면 실제와 다른 것을
재게 된다** — 이번이 그 예다. 🎯 픽스처는 「대충 맞는 것」이 아니라 「서버가 실제로
보내는 것」이어야 한다.

### 함께 — 챕터 카드의 가드를 하나 넓혔다

```
stats !== null  →  stats != null
```

서버는 지금 통계가 없을 때 `myStats` 를 **`null` 로** 보낸다(필드를 빼지 않는다).
그런데 누가 응답에서 `null` 필드를 빼는 설정을 켜면 값이 **없는 것**이 되어 화면이
터진다. 둘 다 「통계 없음」이므로 같이 받는다.

## §8 🔄 남은 네 화면 중 셋을 덮었다 — 그리고 여섯 번째 「서버 문구를 버리는 자리」

§7 을 닫으면서 이렇게 적어 뒀다.

> 맞춤 문제·로그인·가입·채팅 화면은 컴포넌트 검사를 **안 붙였다**. 특히 개념 설명의
> 502·503 구분은 문구를 고르는 «함수» 쪽에서만 덮여 있고 화면이 그것을 실제로
> 보여 주는지는 **안 잰다**.

채팅을 뺀 셋을 덮었다.

### 검사 17건 (55 → 72)

| 어디 | 몇 건 | 무엇을 못 박나 |
| --- | ---: | --- |
| 가입 | 4 | 「틀렸다」와 「너무 많이 틀렸다」를 **상태까지** 다르게 다루는가 |
| 맞춤 문제 | 7 | 개념 설명의 502·503 이 **학생 눈까지** 다른 말로 도착하는가 |
| 로그인 | 6 | 거절 이유 · 세션 만료 안내 · 이메일 형식을 **서버 가기 전에** 막는가 |

#### 가입 — 🎯 `429` 와 `400` 은 «되돌리는 정도» 가 다르다

서버는 인증 코드 입력에 상한을 두고, 상한을 넘기면 **그 코드를 버린다**. 안 버리면
카운터가 만료되길 기다렸다가 같은 코드로 이어서 넣으면 되므로 센 의미가 사라진다.

그런데 화면이 그 `429` 를 **문구로만** 받고 상태를 그대로 두면 이렇게 된다.

```
429 를 받는다 → 「코드를 다시 받아 주세요」가 뜬다
             → 그런데 입력칸이 그대로 있고 숫자도 남아 있다
             → 학생이 다시 눌러 본다
             → 서버에는 코드가 이미 없으므로 「만료되었습니다」
             → 🔴 «시간이 지나서» 그런 줄 오해한다. 실제로는 횟수를 다 쓴 것이다
```

2026-09-15 에 그 분기를 넣었지만 **검사는 못 붙였다**. 여기서 닫았다.

⚠️ 함께 못 박은 것이 더 중요하다 — **`400`(코드 불일치)에서는 되돌리지 않는다.**
숫자 하나 잘못 넣은 학생이 메일을 새로 받아야 한다면 그것도 고장이다.

#### 맞춤 문제 — 🔴 「함수가 맞다」와 「화면이 보여 준다」는 다른 말이다

이 구분을 지키려고 백엔드가 하는 일이 꽤 많다. 챗봇 서버가 실패를 네 종류로 나누고,
메인 서버가 그것을 `429`·`502`·`503` 으로 보존한다(모든 예외를 500 으로 바꾸는
그물보다 **앞에서** 분류한다). §5 에서 화면도 고쳤다.

그런데 §5 의 검사는 **문구를 고르는 함수**를 부를 뿐이었다. 화면이 그 함수를 안 쓰게
바뀌면 여전히 뭉개지는데 아무도 모른다. 이번 검사는 화면을 실제로 그려서
**단원 고르기 → 보기 고르기 → 제출 → 개념 보기**까지 밟는다.

⚠️ 밟아 보고 알게 된 것: 개념 설명 버튼은 **문제를 푼 뒤에만** 나온다. 안 푼 학생에게
개념부터 보여 주면 답을 알려 주는 셈이라 그렇게 돼 있다.

### 🔴 검사를 쓰다가 또 하나 나왔다 — 여섯 번째

맞춤 문제 화면의 **단원 목록 로드**가 이랬다.

```
.catch(() => setError('단원 목록을 불러오지 못했습니다.'))
```

`401` 「로그인이 필요합니다. 다시 로그인해 주세요」가 와도 학생은 **무엇을 하면
되는지**를 못 듣는다. `messageOf` 로 바꿨다.

🎯 **이로써 화면 저장소에서 서버 문구를 버리던 자리는 없다.** 남은 `catch` 둘은
의도된 것이다 — 마이페이지는 이미 서버 문구를 쓰고, 진단 테스트의 JSON 파싱 실패는
「보기 없이 본문만」이 맞는 답이다.

### 🔴 §1 과 «같은 일» 이 또 있었다 — 파일별 숫자 셋이 틀렸다

이 보고서는 §1 을 「어제 적은 숫자 두 개가 틀렸다」로 시작한다. 그런데 오늘 검사를
더 붙이면서 **파일별 건수를 결과 파일에서 집계했더니 또 어긋났다.**

| 문서에 적혀 있던 것 | 실제 | 차이 |
| --- | ---: | ---: |
| `apiError.test.ts` 13건 | **11** | -2 |
| `grades.test.ts` 5건 | **8** | +3 |
| `authStore.test.ts` 5건 | **4** | -1 |
| `./gradlew test` 설명 「인프라 없이 도는 검사 15건」 | **123건** (인프라 필요 11 · 없이 112) | +108 |

⚠️ **합계는 맞았다.** 55건도 288건도 맞는 수였다. 틀린 것은 **쪼갠 내역**이다 —
합계만 재고 내역은 문서에서 옮겨 적었기 때문이다.

🔴 **그리고 나는 하마터면 그 숫자를 그대로 한 번 더 옮길 뻔했다.** 이번 갱신의 첫
판에는 `13 · 5 · 5` 가 그대로 들어가 있었다. 집계를 돌리고 나서야 갈렸다.

🎯 **그래서 규율을 한 줄 더 적었다** — 「건수는 문서에서 옮겨 적지 않는다」가
**합계뿐 아니라 내역에도** 해당한다는 것을 공부 노트와 코드 안내서 양쪽에 못 박았다.
`./gradlew test` 줄 옆에는 **어느 검사가 Oracle·Redis 를 필요로 하는지**도 이름으로
적었다 — 숫자만 있으면 다음 사람이 또 못 확인한다.

## §9 🔴 «남은 일» 자체가 틀려 있었다

§8 을 닫으면서 남은 것을 이렇게 적었다.

> 채팅 화면은 여전히 컴포넌트 검사가 0건이다. **스트리밍이라 재는 방법이 다르다** —
> 응답이 한 번에 오지 않고 조각으로 온다.

**둘 다 사실이 아니다.** 코드를 열어 보고 알았다.

| 적어 둔 것 | 실제 |
| --- | --- |
| 「채팅 **화면**」 | 별도 화면이 아니다. **홈 화면 안의 상자**다 (`Home.tsx:113`) |
| 「스트리밍이라 재는 방법이 다르다」 | 스트리밍이 아니다. `sendChat` 은 **POST 한 번**이고 `answer` 한 덩어리를 받는다 (`ai.api.ts`) |

🔴 **「스트리밍이라 다르다」는 코드를 안 보고 쓴 문장이다.** 그리고 그것을 근거로
「별도 작업」으로 미뤄 뒀다 — **미룬 근거 자체가 없었다.** §1·§8 이 잡은 것과 같은
결함이다. 그때는 숫자였고 이번에는 **일의 성격**이었을 뿐이다.

### 실제로 검사가 없던 곳은 여섯이었다

파일로 세어 보니 하나가 아니라 여섯이었다. 그중 **판단이 걸린 넷**을 덮었다.

| 어디 | 몇 건 | 무엇을 못 박나 |
| --- | ---: | --- |
| `AuthValidator` | 6 | 🔴 **「모른다」를 「로그아웃됐다」로 접지 않는가** |
| 마이페이지 | 7 | 🔴 「미설정」은 학년이 아니다 · 저장이 실패하면 **화면도** 안 바꾼다 |
| 홈의 채팅 | 4 | 🔴 `429` 와 `503` 이 **다른 말**로 보이는가 |
| OAuth 콜백 | 5 | 🔴 성공이든 실패든 **어디로든** 보낸다 |

#### 🔴 `AuthValidator` — 이 저장소의 규칙이 가장 또렷하게 걸린 자리

앱이 뜰 때 「저장된 로그인이 아직 유효한가」를 서버에 한 번 물어본다. 답은 셋이다.

| 서버가 한 것 | 뜻 | 해야 할 일 |
| --- | --- | --- |
| `200` + 사용자 | 로그인이 살아 있다 | 최신 정보로 갱신한다 |
| `401` | 로그인이 **죽었다** | 지운다 |
| 응답 자체가 없다 | **모른다** — 죽었는지 알 수 없다 | 🔴 **지우지 않는다** |

셋째 줄이 전부다. 네트워크가 잠깐 끊긴 것을 「로그아웃됨」으로 접으면 지하철에서 앱을
연 학생이 **이유 없이 로그인 화면으로 튕기고**, 자기가 왜 튕겼는지 알 방법이 없다.

⚠️ 코드는 이미 맞게 돼 있었다(`isUnauthorized(err)` 일 때만 지운다). **검사가 없었을
뿐이다** — 그 조건 한 줄을 지워도 아무도 몰랐다.

#### 🎯 채팅만 실패를 «말풍선» 으로 보여 준다 — 의도된 차이다

다른 화면은 실패를 빨간 문구로 따로 띄우는데 채팅은 답변 자리에 넣는다. **대화 흐름을
끊지 않으려는 선택**이다. 다만 문구는 서버 것을 쓴다 — 「지금은 이용이 몰리고
있어요(429)」는 다시 눌러 볼 일이고 「일시적으로 이용할 수 없습니다(503)」는 기다릴
일이라, 학생이 **할 일이 다르다**.

### 🎯 일부러 안 덮은 둘

`Header` · `Footer` · `NotFound` 는 남겼다. **판단이 없는 화면**이라 검사가 「무엇이
바뀌면 안 되는지」를 못 박지 못하고 **렌더 결과만 굳힌다** — 글자 하나 고칠 때마다
검사가 빨간불이 되고, 그 빨간불은 아무것도 알려 주지 않는다.

## §10 🔴 「맞힐 수 없는 14문제」는 실제로 70문제였다

「무엇부터 할까」에 답하려고 **0절의 14건이 정말 14건인지** DB 를 직접 조회했다.
`PROBLEMS` 의 객관식 500건을 전부 꺼내, **채점이 실제로 하는 일**(정규화 뒤 보기
번호 `1~5` 인가)로 갈랐다.

```
객관식 500건
  정규화 뒤 보기 번호(1~5)  430건   맞힐 수 있다
  그 밖                      70건   🔴 학생이 무엇을 골라도 오답
```

🔴 **14건이 아니라 70건이다.** 500문제의 **14%**다.

### ⚠️ 왜 14 로 세어졌나 — 「자릿수」로 갈랐기 때문이다

2026-09-15 기록은 「보기번호 429 · 12자 이하 57 · **12자 초과 14**」였고, 마지막
14 만 「맞힐 수 없다」로 읽었다. 하지만 **12자 이하여도 보기 번호가 아니면 똑같이 못
맞힌다** — `(해답)③` 도 `①, ③` 도 12자 이하다.

🎯 **재는 잣대를 「길이」가 아니라 「채점이 하는 비교」로 바꾸니 숫자가 다섯 배가 됐다.**
🔴 그리고 430 ≠ 429 다. 보기번호 쪽 수도 한 건 달랐다.

### 모양별 — 대응이 다르다

| | 모양 | 건수 | 예 | 대응 |
| --- | --- | ---: | --- | --- |
| A | 정답 칸이 **비어 있다** | 2 | `텍스트 없음` | 🔴 원본에 없다 |
| B | `(해답)` 접두어 + 보기 번호 | 7 | `(해답)③` | 🎯 **정규화만 넓히면 된다** |
| C | 괄호로 싼 보기 번호 | 7 | `(5)` | 🎯 **정규화만 넓히면 된다** |
| D | 🔴 **복수정답** | **36** | `①, ③` · `②, ⑤` | 결정 하나 |
| E | 풀이 전문이 들어갔다 | 12 | `① 어떤 수를 $a$ 라고 하면 …` | 확인 필요 |
| F | 그 밖 | 6 | `③,텍스트 없음` | 사람이 봐야 한다 |

🔴 **가장 큰 덩어리는 「풀이 전문」이 아니라 「복수정답」 36건이다.** 0절이 대응을
「풀이를 버릴지 해설 칸으로 옮길지」로 적어 뒀는데, **그 판단은 12건에만 해당한다.**

### 🎯 그래서 대응이 세 갈래로 갈린다

- **B·C 14건** — 판단이 필요 없다. `(해답)` 을 떼고 `(5)` 를 벗기면 끝난다.
  ⚠️ 다만 정규화는 채점의 심장이라 **넓히는 만큼 「다른 답이 같아질」 위험**이 는다
  (`AnswerNormalizer` 의 `DoesNotCollide` 검사 5건이 지키는 것이 그것이다).
- **D 36건** — 결정 하나면 풀린다: **`①,③` 과 `③,①` 을 같게 볼 것인가.**
  TODOS 1절에 이미 열려 있는 항목이다.
- **E·F 18건** — 눈으로 보면 **맨 앞 글자가 보기 번호**다(`① 어떤 수를…`).
  ⚠️ 하지만 `③ ① 이차식이다. ② 항은…` 처럼 **풀이 안에도 원문자가 들어 있다.**
  「맨 앞 것이 정답」이 18건 전부에 맞는지는 **사람이 표본을 봐야 안다** — 여기서
  기계적으로 앞 글자를 떼면 틀린 정답을 «맞는 것처럼» 만든다.

### 🔴 재는 방법

```
docker exec -i oracle23ai sqlplus -s <계정> …
  select id, answer from problems where problem_type = 'MULTIPLE_CHOICE'
→ AnswerNormalizer.normalize 의 핵심(원문자→숫자 · $ 공백 중괄호 제거)을 옮겨
  정규화한 뒤 결과가 '1'~'5' 인지로 가른다
```

⚠️ **자릿수로 세면 안 된다.** 그게 이번 오차의 원인이다.

## §11 🔄 결정 없이 고칠 수 있던 14건을 고쳤다 — 그리고 21건이 더 나왔다

§10 이 가른 여섯 무리 중 **B·C 14건은 사람 판단이 필요 없다.** 고쳤다.

### 무엇을 고쳤나

```
(해답)③  →  3     7건
(5)      →  5     7건
```

🎯 **일반 정규화에 넣지 않았다.** `AnswerNormalizer.normalize` 는 「표기 차이」를
흡수하는 자리인데 이건 「자료가 더러운 것」이고, **객관식에서만 참이다.**
단답형 채점을 서버로 되돌릴지가 아직 열린 결정인데 그때 `(5)` 를 `5` 로 벗기면
**순서쌍이나 괄호가 뜻을 가지는 답을 뭉갠다.**

그래서 `stripChoiceNoise` 를 따로 두고 `matchesChoice` 에서만 쓴다.

```
normalize        표기 차이를 흡수한다            (모두에게 참)
stripChoiceNoise 자료 잡음을 걷어낸다            (객관식에서만 참)  ← 새로 만든 것
matchesChoice    normalize → stripChoiceNoise → 비교
```

### 🔴 「통째로 그 모양일 때만」 걷어낸다

정답 칸에 풀이가 통째로 들어온 건이 12건 있고, 거기엔 `\left(-\frac{1}{3}\right)`
같은 수식이 있다. **거기서 괄호를 벗기면 다른 수가 된다.** 그래서 두 규칙 다
문자열 전체가 그 모양일 때만 걸리게 고정했다.

⚠️ `(해답)` 접두어도 **뒤에 보기 번호 하나만 남을 때만** 뗀다. DB 의 7건이 전부
그 모양이었고, **본 적 없는 모양으로 규칙을 넓히지 않는다** — 못 맞히는 쪽이
틀리게 맞히는 쪽보다 낫다.

### 잰 것

| | |
| --- | ---: |
| 객관식 | 500건 |
| 고치기 전 맞힐 수 없던 것 | 70건 |
| **고친 뒤** | **56건** |
| 🎯 되살아난 문제 | **14건** |

🔴 **검사가 초록불인 것과 자료가 실제로 고쳐진 것은 다른 말이다.** 검사는 내가 고른
예시 몇 개를 볼 뿐이라, DB 500건에 규칙을 **다시 전수로** 대 봤다.

### 🔴 재다가 또 나왔다 — 보기가 «하나도 없는» 문제 21건

정답 칸을 보다가 **문제 본문**도 세어 봤다.

```
본문에 보기 원문자가 5개  477건
                     4개    2건
                     0개   21건   ← 🔴 고를 것이 화면에 안 나온다
```

이 21건은 `OPTIONS` 컬럼도 `null` 이다. 화면은 본문에서 보기를 뽑고, 못 뽑으면
**보기 없이 본문만** 그린다. 그런데 제출 버튼은 「고른 것이 있어야」 눌린다 —
**막다른 길이다.**

⚠️ 그중 19건은 **정답 칸이 멀쩡하다.** 즉 §10 의 70건과 거의 겹치지 않는다.

```
학생이 못 푸는 객관식 = 70(정답 칸) + 19(보기 없음) = 89건 / 500건 = 18%
  → 이번에 14건을 고쳐  75건 / 500건 = 15%
```

🎯 **PRD §2 ② 의 「객관식(4지선다)」도 정확하지 않다** — 실제로는 **5지선다가 477건**,
4지선다는 2건이다.

  그것은 jsdom(브라우저를 흉내 낸 것) 위에서 그린 것이다. **실제 브라우저에서 같은지는

- 🔄 **이 항목은 §9 에서 닫혔다** — 다만 「채팅 화면」이라는 말 자체가 틀렸다. 채팅은

  `NotFound` 셋이고, ⚠️ **이건 일부러 남긴 것이다** — 판단이 없는 화면이라 검사가

  그대로 도는지는 다른 문제다
- 어제 커밋 메시지에 남은 틀린 숫자는 **고칠 수 없다.** 이미 머지됐고, 이력을 다시 쓰지
  않는 것이 규율이다
