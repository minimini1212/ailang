# 난이도는 어디서 왔나 — 2026-09-07

> **본 날짜: 2026-09-07**
> **무엇을 했나**: DB 에 저장된 문제 1,132건의 난이도가 원본 JSON 의 어느 값에서 나왔는지
> 전수로 찾았다. **결론: 어디서도 나오지 않는다.**
> **어떻게**: DB 를 읽기 전용으로 덤프해 원본과 본문으로 짝짓고(1,132/1,132 전부 성공),
> `question_info` 의 12개 필드 전부와 그 조합을 대조했다.
>
> 🔴 이 문서는 **재료**다. 대응은 [`../../TODOS.md`](../../TODOS.md) 와
> [`../DATA_CONTRACT.md`](../DATA_CONTRACT.md) 로 간다.

## §0. 이 문서를 처음 보는 사람에게

| 말 | 뜻 |
| --- | --- |
| **난이도 축** | 하(LOW)·중(MEDIUM)·상(HIGH). 학생 정답률에 따라 이 축을 오르내린다. |
| **원본 JSON** | AI Hub 에서 받은 문제 파일. 문제마다 학년·단원·유형 같은 값이 붙어 있다. |
| **적재** | 그 JSON 을 읽어 DB 를 채우는 작업(`DataLoader`). |
| **설명력** | 「그 필드값이 같으면 난이도도 같은가」의 비율. 100% 면 그 필드가 난이도를 정한 것이다. |
| **과적합** | 값의 종류가 너무 많아 «설명한 것처럼 보이는» 상태. 규칙이 아니다. |

## §1. 왜 찾았나

지금 DB 에는 난이도가 **하454 · 중432 · 상246** 으로 고르게 들어 있다.
그런데 **같은 원본 자료를 현재 코드로 다시 적재하면 하1131 · 중21 · 상0** 이 된다
([`aihub-data-measurement-2026-08-31.md`](aihub-data-measurement-2026-08-31.md) §1).

즉 지금 DB 는 **다시 만들 수 없는 상태**였다. 비우면 되돌릴 수 없고, 재적재하면
진단 테스트(상 6문제 필요)가 깨진다.

그래서 「그 값이 대체 어디서 왔나」를 먼저 찾기로 했다. 찾으면 재현되고, 못 찾으면
그 사실 자체가 결정의 근거가 된다.

---

## §2. 🔴 결론 — 원본으로는 만들 수 없다

### 단일 필드

| 필드 | 값 종류 | 설명력 |
| --- | --- | --- |
| **`question_unit`** (단원 번호) | 8 | **86.4%** |
| `question_topic` (소단원 코드) | 329 | 90.6% ⚠️ 과적합 |
| `question_sector2` (영역) | 4 | 62.4% |
| `question_term` (학기) | 2 | 59.9% |
| `question_step` (기본/실생활응용) | 2 | 42.0% |
| `question_difficulty` (1~3) | 3 | 44.8% |
| 나머지 6개 | 1~4 | 40~56% |

⚠️ `question_topic` 의 90.6% 는 **값이 329종인데 문제가 1,132건**이라 나온 숫자다.
한 값에 평균 3.4문제뿐이라 「같은 값이면 같은 난이도」가 저절로 높아진다. 규칙이 아니다.

### 두 필드 조합

최고가 `question_topic + question_sector1` 의 93.2% 인데 **조합이 504종**이다.
역시 과적합이고, 규칙으로 쓸 수 없다.

### 🎯 결정적 증거 — 단원 안에서는 어떤 필드도 정보가 없다

`question_unit` 이 86.4% 로 가장 높은 것은 우연이 아니다. 교차표가 단조롭다.

```
unit 01 → 하 73  중  1  상  1
unit 02 → 하165  중  0  상  0
unit 03 → 하177  중 64  상  0
unit 04 → 하  0  중104  상  0
unit 05 → 하  0  중180  상  0
unit 06 → 하  0  중 72  상 49
unit 07 → 하  0  중  0  상168
unit 08 → 하 39  중 11  상 28
```

단원 02·04·05·07 은 **100% 순수**하다. 뒤 단원일수록 어렵다 — 교육과정상 자연스럽다.

그런데 **03·06·08 안에서 갈리는 것을 설명하는 필드가 하나도 없다.**

```
unit 03 (하177 / 중64) 안에서
  question_term        73.4%      ← 177/241 = 다수결 기준선
  question_type1       73.4%      ← 같음
  question_step        73.4%      ← 같음
  question_difficulty  73.4%      ← 같음
  … 9개 필드 전부 73.4%
```

🔴 **모든 필드가 다수결 기준선과 «정확히» 같다.** 이것은 그 필드들이 난이도에 대해
**정보를 0 만큼 갖고 있다**는 뜻이다.

### 진도 순서 가설도 아니다

「단원 안에서 뒤쪽 소단원이 어렵다」를 의심해 `question_topic` 코드 순서와 대조했다.

| 단원 | 역전 쌍 | 판정 |
| --- | --- | --- |
| unit 01 | 19 / 378 | 거의 단조 (예외 1건) |
| unit 03 | **290 / 2485** | ❌ |
| unit 06 | 116 / 820 | ❌ |
| unit 08 | **142 / 435** | ❌ (3쌍 중 1쌍이 역전) |

### `question_difficulty` 를 그대로 쓰면?

`1→하 · 2→중 · 3→상` 으로 매핑하면 지금 DB 와 **33.7%** 만 맞는다.
**3문제 중 2개의 난이도가 달라진다.**

## §3. 그래서 무엇을 했나 — 유도 대신 기록

유도할 수 없다고 **재현**까지 못 하는 것은 아니다.

`src/main/resources/data/difficulty-overrides.csv` 에 **「원본 id → 난이도」 1,132줄**을
기록하고, 적재할 때 이 표를 먼저 본다. 없으면 기존 매핑으로 떨어진다.

### 검증 — 계산으로 대조했다

| | 분포 | 지금 DB 와 일치 |
| --- | --- | --- |
| **스냅샷 사용** | 하472 · 중436 · 상244 | **99.8%** (1130/1132) |
| 스냅샷 없이 원본 필드만 | 하1131 · 중21 · **상0** | 41.0% (464/1132) |

### ⚠️ 못 맞히는 2건 — 원리적 한계다

본문이 **완전히 같은데 DB 에서 난이도가 다른** 문제가 있다.

```
"다음 그림에서 $\angle x$ 의 크기를 구하여라."   → 중 6건 · 상 1건
"다음 그림에서 $∠x$ 의 크기를 구하여라."         → 중 1건 · 상 1건
```

그림이 본문 텍스트에 없어서(이미지다) 구분할 방법이 없다. `PROBLEMS` 에 원본 `id`
컬럼이 없어 DB 쪽에서도 짚을 수 없다.

🎯 **1,132건 중 2건(0.2%)이 상 대신 중으로 적재된다.** 이 이상은 지금 구조로 못 올린다 —
쫓지 않고 여기 적어 둔다.

## §4. 이 표는 규칙이 아니라 기록이다

🔴 **오해하지 말 것**: 이 파일은 「난이도를 이렇게 정한다」가 아니라
「누군가 이렇게 정해 뒀더라」의 기록이다.

- **새 학년 자료에는 이 id 가 없다.** 기존 매핑으로 떨어지고, 그러면 상(HIGH) 이
  한 건도 안 나온다. 적재 로그가 그 건수를 알려 준다.
- **난이도 축을 «무엇으로 정할 것인가» 는 여전히 결정 대기다**
  ([`../../TODOS.md`](../../TODOS.md) 0절·8절). 이번 작업은 그 결정을 **급하지 않게**
  만든 것이지 대신한 것이 아니다.
