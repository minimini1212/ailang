## §1. 🔴 가장 중요한 발견 — 지금 DB 는 **현재 코드로 재현할 수 없다**

### 실측

| | 하(LOW) | 중(MEDIUM) | 상(HIGH) | 합계 |
| --- | --- | --- | --- | --- |
| **지금 DB 에 들어 있는 것** | 454 | 432 | 246 | 1,132 |
| **현재 코드가 이 JSON 으로 만들 것** | **1,131** | **21** | **0** | 1,152 |

### 같은 데이터가 맞다 — 확인했다

DB 문제 본문 10건(상 5 · 하 5)을 뽑아 JSON 에서 찾았다. **10건 전부 있었다.**
본문 기준 JSON 고유 문제 수도 **1,132** 로 DB 와 정확히 같다.
챕터 수도 양쪽 **331** 로 같고, 학년은 전부 `MIDDLE_1`(원본 `M1`)이다.

그런데 **상(HIGH)으로 저장된 5건이 JSON 에서는 전부 `question_step = 기본`** 이었다.

```
DB=HIGH   JSON=LOW  (step=기본, score=2)   00041_42257
DB=HIGH   JSON=LOW  (step=기본, score=2)   00041_97547
DB=HIGH   JSON=LOW  (step=기본, score=3)   00041_97561
DB=HIGH   JSON=LOW  (step=기본, score=1)   00041_97571
DB=HIGH   JSON=LOW  (step=기본, score=3)   00041_97591
```

### 왜 이렇게 됐나

원본에 실제로 있는 `question_step` 값은 **둘뿐**이다.

```
기본        935건
실생활응용   217건
```

그런데 코드의 매핑은 `기본→LOW · 표준→MEDIUM · 심화→HIGH` 다
(`DataLoader.java:53~57`). **`표준`과 `심화`가 데이터에 없다.**
`실생활응용` 은 매핑에 없어 `question_difficulty` 점수로 떨어지는데, 그 점수도
**최댓값이 3** 이라 `difficultyFromScore`(`>3` 이어야 HIGH)가 **HIGH 를 낼 수 없다.**

```
question_difficulty 전체 분포:  1→227건,  2→627건,  3→298건   (4·5 없음)
```

🔴 **즉 이 JSON 으로는 어떤 경로로도 HIGH 가 나오지 않는다.**
지금 DB 의 246건은 **다른 방법으로 들어간 값**이다 — git 이력상 `STEP_MAP` 은 바뀐 적이
없고(`DataLoader` 는 `01802c1` 에서 처음 등장), `AILANG` 스키마는 그보다 이른
2026-02-23 에 만들어졌다. 사람이 손으로 넣었거나, 커밋되지 않은 다른 코드가 넣었다.

### 왜 — 챕터가 너무 잘게 쪼개져 있다

`question_topic_name` 을 챕터로 쓰는데, 실제 값이 단원이 아니라 **유형**이다.

```
챕터 수                331개
챕터당 평균            3.5문제
문제 1개짜리 챕터      93개
문제 3개 이하 챕터     200개  (60%)
```

예: `평행선에서 각의 크기 구하기(3)-보조선 2개` · `맞꼭지각(1)` · `다면체의 면의 수`

🔴 **난이도 조정은 챕터당 3문제 이상 풀어야 시작된다**(`UserChapterStats:71`).
챕터의 60% 가 3문제 이하이므로 **그 챕터들은 난이도가 영원히 안 움직인다.**

⚠️ `order_num`(표시 순서)으로 쓰는 `question_unit` 은 **서로 다른 값이 8개뿐**인데
챕터는 331개다. 즉 한 순번에 챕터 28~71개가 몰린다 — 표시 순서가 사실상 정해지지 않는다.

```
order_num:  1→28  2→32  3→71  4→26  5→51  6→42  7→50  8→31
```

📌 문제가 하나도 없는 챕터가 **2개** 있다.

## §5. `normalizeAnswer` 충돌 — 24그룹 중 **나쁜 건 3그룹**

서로 다른 원문이 정규화 후 같은 값이 되는 그룹 24개를 찾았다. 그중:

**✅ 21그룹은 의도된 동작** — 표기 차이만 흡수했다.
```
'1,5'  <-  ['①, ⑤', '①,⑤']          공백 차이
'2'    <-  ['②', '2', '$2$']          원문자/달러 표기 차이
'3'    <-  ['$3$', '$3 $', '③']
```

**🔴 3그룹은 뜻이 다른데 뭉개졌다.**
```
'8'    <-  ['$ 8 \pi $', '$8  $', '$8$']       ← 8 과 8π 가 같아진다
'65^'  <-  ['$ 65^{\circ} $', '$65^{\degree}$'] ← 표기 2종 (같은 값이라 무해)
''     <-  ['$', '$\bigcirc$']                  ← 둘 다 빈 문자열
```

정규화 결과가 **빈 문자열**이 되는 정답은 전체 **2건**이다
(`'$'` 와 `'$\bigcirc$'`). 이 2건은 학생이 `"$"` 한 글자만 내도 정답 처리된다.

뜻이 바뀌는 명령어(`\pi` `\sqrt` `\alpha` 등)를 포함한 정답은 **49건**이지만,
대부분 단답형이라 자가채점 경로로 가고 서버 비교를 안 탄다.

🎯 **정리**: 이 결함은 실재하지만 **지금 대량으로 오채점을 내고 있지는 않다.**
객관식 98% 가 원문자라 정상 처리된다.

## §8. ⚠️ `.env` 가 깨져 있다 (2026-08-31 발견)

`.env` 의 **모든 줄 앞에 `; ` 가 붙어 있다.**

```
; # Oracle DB (Docker Oracle 23ai)
; DB_USERNAME=...
; DB_PASSWORD=...
```

`;` 는 dotenv 주석 문자가 아니고, 설령 주석으로 읽히더라도 **모든 키가 사라진 것과 같다.**
IDE 에서 파일 전체를 선택하고 「주석 처리」(Ctrl+/)를 누르면 나오는 모양이다.

🔴 **이 상태로는 Spring 이 뜨지 않는다.** 그리고 `.env` 는 Claude 가 쓰지 않는 파일이므로
(레포 HARD RULE) 사용자가 직접 고쳐야 한다.

📌 덧붙여 `.env` 에 `DATA_PROBLEM_DIR` · `DATA_ANSWER_DIR` 이 **아직 없다.**
`application.yml` 이 이제 이 키를 읽으므로 채워야 한다
([`../../.env.example`](../../.env.example) ⑦).

경로는 이것이다:
```
DATA_PROBLEM_DIR=C:/Users/USER/OneDrive/Desktop/project/ailang/jsonFile/problem/1st-grade
DATA_ANSWER_DIR=C:/Users/USER/OneDrive/Desktop/project/ailang/jsonFile/answer/1st-grade
```
