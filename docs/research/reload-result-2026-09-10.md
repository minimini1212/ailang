## §2. 🔴 새 발견 — **20건이 조용히 빠지고 있었다**

원본은 1,152건인데 DB 는 1,132건이다. **예전 DB 도 1,132건이었다** — 즉 이 누락은 이번에
생긴 것이 아니라 **처음부터 있었고 아무도 몰랐다.**

원본 id 와 DB 의 `SOURCE_ID` 를 대조해 빠진 20건을 특정하고, 무엇이 다른지 쟀다.

```
저장된 1,132건 — 정답 글자수 최대  190
빠진     20건 — 정답 글자수 최소  213
```

🎯 **정확히 갈린다.** `PROBLEMS.ANSWER` 가 `VARCHAR2(200)` 이라, 정답이 200자를 넘는 문제는
저장에서 예외가 나고 `LoadOutcome.ERROR` 로 세어진 뒤 버려진다.

```
원본에서 200자 초과인 문제        20건
그중 DB 에 없는 것                20건   ← 100% 일치
```

### 왜 정답이 200자를 넘나

원본의 `answer_bbox` 에서 `type=="answer"` 인 칸에 **정답과 풀이가 함께** 들어 있는 경우다.

```
00043_09957  ①, ④  ① $A$ 중학교에서 상대도수가 가장 큰 계급은 …   (1,106바이트)
00042_04206  ⑴ <table border> … (표 전체가 정답 칸에 들어 있다)
```

### 이게 왜 문제인가

- 🔴 **오류가 로그에만 남고 화면에는 안 보인다.** 「1,152건 중 1,132건 저장」이라고 찍히지만,
  그 20건이 **왜** 빠졌는지는 사유 집계에서 `처리 중 오류` 한 덩어리로만 보인다.
- 🔴 **자료가 치우친다.** 빠진 20건은 대부분 **서술형·표가 있는 문제**다. 즉 «긴 답을 요구하는
  문제»가 통째로 빠진 자료로 학생 수준을 재고 있다.
- ⚠️ 이 결함은 리뷰가 `OPTIONS(1000)` 에서 지적한 것과 **같은 모양**이다 — 컬럼 폭을 넘는 값이
  저장 단계에서 터지는데, 그것을 **저장 전에 검사하지 않는다.**

🧭 **대응은 사용자 결정이다** — 컬럼을 넓힐지(CLOB), 정답만 잘라 담고 나머지를 해설로 보낼지,
그 20건을 버릴지는 **채점 방식과 얽힌 판단**이다 (`TODOS.md` 8절).
